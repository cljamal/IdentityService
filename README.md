# IdentityService

IdentityService — сервис регистрации и аутентификации пользователей для независимых
проектов. Он принимает запросы от Шлюза проекта, проверяет учётные данные пользователя,
выдаёт JWT и управляет жизненным циклом аккаунта: подтверждением контактов,
восстановлением пароля, сменой телефона, активными сессиями и удалением.

Один экземпляр приложения и одна БД обслуживают нескольких **клиентов**. Клиент здесь —
подключённый проект, а не пользователь или устройство. Один телефон, email или username
может существовать у разных клиентов как несколько независимых аккаунтов.
Общего аккаунта между проектами и SSO нет.

API использует собственный guard `id-api` поверх `php-open-source-saver/jwt-auth`.
Пользователь аутентифицируется токеном, без браузерных сессий и cookies Laravel.
При этом сервис хранит состояние OTP и токеновых сессий, необходимое для проверки
сроков действия, ротации и немедленного отзыва доступа.

## Как проходит запрос

```text
Пользователь → Шлюз проекта → IdentityService
                              │
                              ├─ client middleware → CurrentClient
                              ├─ id-api guard, если нужен пользователь
                              └─ Controller → Action → Strategy / Repository
                                                       └─ Events → Listeners
```

Каждый запрос к `/api/auth/*` передаёт:

```http
Accept: application/json
Content-Type: application/json
X-Client-Id: <публичный идентификатор проекта>
X-Client-Secret: <секрет проекта>
```

Для защищённых операций дополнительно нужен `Authorization: Bearer <access_token>`.
Секрет клиента предназначен для Шлюза; его нельзя передавать в публичный frontend.

`AuthenticateClient` проверяет активность клиента и хеш секрета, затем заполняет
`CurrentClient`. На маршрутах с двумя проверками клиент определяется **до**
`auth:id-api`: guard должен знать, какому проекту принадлежит запрос.
Этот порядок закреплён в [bootstrap/app.php](bootstrap/app.php).

Поиск идентификаторов и проверка уникальности учитывают клиента и провайдера.
OTP для входа, регистрации и восстановления также разделяются по клиенту;
операции над аккаунтом используют идентификатор конкретного пользователя.
Токен одного проекта не даёт доступ через credentials другого.

## Провайдеры и доступные операции

Провайдер выбирается сегментом URL: `phone-otp`, `email-password` или
`username-password`. Каждый независимо включается в
[config/identity.php](config/identity.php) через `AUTH_PROVIDER_*_ENABLED`.

| Возможность | `phone-otp` | `email-password` | `username-password` |
| --- | --- | --- | --- |
| Вход | Телефон + OTP | Email + пароль | Username + пароль |
| Регистрация | При первом успешном входе | Отдельная, с подтверждением email | Отдельная; подтверждение при наличии rescue-контакта |
| Восстановление пароля | Нет пароля | Код на email | Код на найденный rescue-контакт |
| Смена пароля | Не поддерживается | Текущий и новый пароль | Текущий и новый пароль |
| Смена идентификатора | Подтверждение старого и нового телефона | Не поддерживается | Не поддерживается |
| Удаление аккаунта | Код на привязанный телефон | Код на привязанный email | Не поддерживается |

Маршруты общие для провайдеров, но доступность определяется capability-контрактами
стратегии. Неподдерживаемая операция возвращает `400 UNSUPPORTED_AUTH_OPERATION`;
выключенный провайдер — `404 AUTH_PROVIDER_DISABLED`.

Телефон нормализуется до цифр без `+`, пробелов и скобок. Затем проверяются формат
и разрешённые страны: сейчас в конфигурации указан Узбекистан (`998`),
управляемый `PHONE_COUNTRY_UZ_ENABLED`. Email обрезается по краям и приводится
к нижнему регистру до валидации и поиска.

### Вход и регистрация

**Телефон.** Запрос `otp` сохраняет код и инициирует доставку.
Успешный `login` находит аккаунт текущего клиента или создаёт его, отмечает
телефон подтверждённым и выдаёт пару токенов. Код удаляется после успешного
поиска/создания пользователя. Отдельный `register` для телефона не нужен.

**Email.** `register` создаёт пользователя и неподтверждённую identity с хешем
пароля, отправляет код и возвращает сообщение без токенов.
`register/verify` подтверждает identity и выдаёт токены.
Вход до подтверждения возвращает `403 IDENTITY_NOT_VERIFIED`.

**Username.** Регистрация сразу подтверждается и выдаёт токены, если rescue-контакт
не найден. Если контакт есть, сначала требуется подтверждение кодом.

Новые пароли требуют минимум 8 символов и `password_confirmation`.
Пароль хранится хешем в данных соответствующей identity.

### Восстановление и смена пароля

`password/forgot` создаёт код восстановления. Для email он отправляется только
при найденной identity. Для username `RescueContactResolver` ищет контакт по цепочке:

1. Подтверждённая `email-password` identity того же пользователя.
2. Подтверждённая `phone-otp` identity того же пользователя.
3. Дополнительная EAV-таблица, если задана `AUTH_USERNAME_PASSWORD_RESCUE_TABLE`.

Параметры колонок этой таблицы и ключ контакта задаются через
`AUTH_USERNAME_PASSWORD_RESCUE_*`. Для другого источника можно реализовать
`RescueContactResolver` и изменить binding в `AppServiceProvider`.
Отдельного публичного API привязки identities сейчас нет.

Отсутствие пользователя или rescue-контакта не раскрывается ответом `forgot`:
код и cooldown сохраняются, но доставка без адресата не выполняется.
Успешный ответ не гарантирует, что пользователь получил сообщение.

`password/reset` проверяет код, меняет пароль, подтверждает identity и записывает
историю. Затем отзывает **все прежние сессии** пользователя и выдаёт новую пару
токенов. Обычный `password/change` требует авторизованного пользователя и текущий
пароль; в существующей реализации он не отзывает сессии.

## JWT, refresh tokens и сессии

Успешный вход, завершённая регистрация и сброс пароля возвращают ресурс:

```json
{
  "data": {
    "access_token": "<JWT>",
    "refresh_token": "<непрозрачный токен>",
    "token_type": "bearer",
    "expires_in": 3600,
    "refresh_expires_in": 1209600
  }
}
```

Числа приведены для стандартных TTL: `JWT_TTL=60` и
`AUTH_REFRESH_TOKEN_TTL=20160` минут. Поля ответа выражены в секундах.
Refresh TTL относится к собственной реализации сервиса, а не к
`JWT_REFRESH_TTL` библиотеки.

JWT содержит публичный UUID пользователя в `sub`, роль в `role` и публичный
идентификатор клиента в `client_id`. Внутренний числовой ID пользователя
используется для связей в БД.

Каждый вход создаёт запись `auth_sessions`: текущий `jti`, хеш refresh token,
сроки действия, IP, User-Agent и время использования. Refresh token хранится
в БД только в виде хеша.

`POST /api/auth/refresh` принимает `{"refresh_token": "..."}` и credentials
клиента. Действующий access token для этой операции не требуется.

При обновлении сервис:

1. Проверяет refresh token, срок действия, отзыв сессии и принадлежность клиенту.
2. Выпускает новую пару и атомарно обновляет ту же запись сессии.
3. Сохраняет предыдущий хеш для обнаружения повторного использования.

Ротация меняет `jti`, поэтому предыдущий access token тоже перестаёт работать.
Срок refresh продлевается от момента успешной ротации; новая сессия не создаётся.
На стороне Шлюза следует координировать обновления одной сессии.

Повторное предъявление токена, совпавшего с сохранённым предыдущим хешем,
отзывает сессию и возвращает `401 REFRESH_TOKEN_REUSED`.
Хранится только один предыдущий хеш, а не история всех ротаций.
Если два запроса уже прочитали текущий токен и конкурируют за обновление,
проигравший атомарную запись получает `401 INVALID_REFRESH_TOKEN`,
не отзывая сессию победителя.

Guard сверяет токен с текущей записью сессии и актуальным состоянием клиента.
Одной корректной подписи JWT недостаточно для доступа.

`GET /api/auth/sessions` показывает неотозванные сессии с действующим refresh token,
даже если их access token уже истёк. Ответ содержит IP, User-Agent, даты и
`is_current`; поле `expires_at` — срок access token, а не refresh token.
`DELETE /api/auth/sessions/{session}` отзывает только сессию текущего пользователя.
`logout` отзывает текущую сессию и инвалидирует её токен.

## Смена телефона и удаление аккаунта

Смена телефона выполняется в три шага под авторизацией пользователя:

1. `identifier/change` с `new_phone`: проверка номера и отправка кода на старый.
2. `identifier/change/confirm-old` с `code`: подтверждение старого номера,
   затем отправка нового кода на новый номер.
3. `identifier/change/confirm-new` с `code`: замена идентификатора,
   запись истории и событие `user.phone_changed`.

Ожидаемый номер и коды хранятся временно в Redis. При переходе ко второму коду
срок хранения ожидаемого номера обновляется. Новый номер должен быть свободен
в рамках текущего клиента и провайдера.

Удаление начинается с `account/delete`: код отправляется на привязанный телефон
или email. `account/delete/confirm` проверяет его и запускает `DeleteAccountAction`.

В транзакции освобождаются все идентификаторы пользователя, отзываются сессии,
выполняется soft delete аккаунта и записывается история. Затем инвалидируется
токен текущего запроса и отправляется `user.account_deleted`.
Освобождённые телефон/email/username можно зарегистрировать заново.
Это soft delete для учёта истории; публичного восстановления аккаунта нет.

## Архитектура: Actions + Events

Основные сценарии оформлены Action-классами с `AsAction` и `handle()`,
вызываемыми через `::run()`. Общего слоя `AuthService` нет.

| Часть | Ответственность |
| --- | --- |
| [Controllers](app/Http/Controllers/) | HTTP-вход, вызов Action, сериализация результата |
| [Actions/Auth](app/Actions/Auth/) | Сценарий, проверка capability, нормализация/валидация и координация |
| [Strategies](app/Auth/Strategies/) | Правила и поведение конкретного провайдера |
| [Support](app/Auth/Strategies/Support/) | Общие механики OTP, верификации, восстановления и смены телефона |
| [Repositories](app/Repositories/) | Хранение identities, сессий, истории, ролей и OTP |
| [IdApiGuard](app/Auth/Guards/IdApiGuard.php) | Проверка JWT, выпуск пары, ротация и отзыв |
| [Events](app/Events/) / [Listeners](app/Listeners/) | Внутренние реакции, доставка и сигналы для Шлюза |
| [Resources](app/Http/Resources/) / [AuthException](app/Exceptions/Auth/AuthException.php) | Форматы успешных ответов и доменных ошибок |

Интерфейсы репозиториев и notifier-ов связаны с реализациями в
[AppServiceProvider](app/Providers/AppServiceProvider.php).
Существующие support-классы остаются самостоятельными участниками сценариев.

### Модель данных и роли

- `clients` — проекты, хеши секретов и флаг активности.
- `users` — аккаунты конкретного клиента, публичный UUID и soft delete.
- `auth_providers` — идентификаторы, данные провайдера и дата подтверждения.
- `auth_sessions` — состояние токеновых сессий и ротации.
- `identity_change_logs` — регистрация, подтверждение, изменения пароля,
  телефона, освобождение идентификаторов и удаление аккаунта.

Роли реализованы через `spatie/laravel-permission` для guard `id-api`.
Создание пользователя вызывает `UserHasNoRole`; синхронный listener
`AssignDefaultRole` назначает `user` ещё внутри транзакции создания.
Роль доступна до выпуска JWT. Изменение роли не переписывает уже выданный JWT;
новый токен получает актуальное значение claim.

### OTP и доставка

Код состоит из 4 цифр, действует **90 секунд**; повторный запрос разрешён через
**60 секунд**. Сроки заданы в [RedisOtpRepository](app/Repositories/RedisOtpRepository.php).
Route throttling дополнительно ограничивает частоту HTTP-запросов.

```text
Strategy / Support → сохранение OTP → OtpCodeIssued
                                      └─ RouteOtpCodeDelivery
                                          ├─ OtpCodeBroadcast
                                          └─ OtpCodeDeliveryRequested
                                              └─ DeliverOtpCode
                                                  └─ SmsNotifier / EmailNotifier
```

Событие мониторинга `otp.issued` содержит канал доставки, назначение, маскированный
контакт и время. Код, SMS-шаблон, его данные и готовый текст присутствуют только
во внутренней цепочке доставки и не передаются в broadcast.

### Текст SMS от подключённого сервиса

Шлюз может добавить необязательный блок `sms` в JSON запроса, который выдаёт OTP:

```json
{
  "phone": "998901234567",
  "sms": {
    "template": "Добро пожаловать в {{service_name}}! Ваш код {{code}}. Не передавайте его никому.",
    "data": {
      "service_name": "Мой сервис"
    }
  }
}
```

`template` обязательно содержит `{{code}}`: IdentityService подставляет свой
сгенерированный код. Остальные подстановки берутся из `data`; имя переменной
состоит из латинских букв, цифр и `_`, начинается с буквы или `_`.
Значения — строки, числа или boolean, которые приводятся к строке.
`data` можно опустить, если дополнительных переменных нет.
Передавать `data.code`, вложенные значения, `null` или неизвестные поля в `sms` нельзя.
Каждая переменная шаблона должна иметь значение.

Подстановка буквальная, без Blade, PHP и повторной обработки значений.
Некорректный блок `sms` возвращает стандартный `422` с `errors` до записи
пользователя или OTP. Если блок полностью отсутствует, используется
`Ваш код подтверждения: {{code}}`; пустой или некорректный блок не включает fallback.

Блок принимается в запросах `otp`, `register`, `password/forgot`,
`identifier/change`, `identifier/change/confirm-old` и `account/delete`
для провайдеров, поддерживающих соответствующую операцию.
Для username текст используется, когда rescue-контакт — телефон.
Если доставка идёт на email, SMS-шаблон не меняет её содержимое.

При смене телефона `identifier/change` задаёт текст для **старого** номера,
а `identifier/change/confirm-old` — для **нового**. Шаблон передаётся заново
в каждом запросе и не сохраняется в БД или OTP-хранилище.
Шлюз выбирает текст, а общий канал и получателя по-прежнему определяет IdentityService.

[RenderOtpSmsAction](app/Actions/Auth/RenderOtpSmsAction.php) формирует сообщение
перед вызовом `SmsNotifier`; notifier получает готовый текст, а не отдельный код.
Пока [LoggingSmsNotifier](app/Notifications/Otp/LoggingSmsNotifier.php) пишет его в лог.
Пример запроса — [Send Code Custom SMS](dev/IdentityService/Phone%20OTP/Send%20Code%20Custom%20SMS.bru)
в Bruno. Переменные `code` и `service_name` в нём оставлены для IdentityService;
не создавайте одноимённые переменные Bruno.

### События для Шлюза

Ops-события адресованы приватному каналу `client.{client_id}`,
где используется публичный идентификатор проекта:

| Событие | Значение |
| --- | --- |
| `user.registered` | Завершённая регистрация, включая первый вход по телефону |
| `user.phone_changed` | Подтверждённая смена телефона |
| `user.session_revoked` | Отзыв сессии/сессий с указанием причины |
| `user.account_deleted` | Завершённое удаление аккаунта |
| `user.refresh_token_reuse_detected` | Обнаружение предыдущего refresh token |
| `service.disabled` / `service.enabled` | Изменение активности клиента |
| `ops.test` | Диагностический сигнал |

Они используют `ShouldBroadcastNow` и `ShouldRescue`: broadcast выполняется
синхронно, а ошибка транспорта репортится без превращения завершённой auth-операции
в HTTP 500. Это не очередь с гарантированной доставкой.
У `OtpCodeBroadcast` отдельный контракт без `ShouldRescue`.

Авторизация подписок разделена:

- `POST /api/broadcasting/client-auth` — credentials клиента и доступ Шлюза
  только к своему каналу.
- `POST /api/broadcasting/auth` — пользовательский JWT; без браузерных cookies/CSRF.
  Текущий канал `otp-deliveries` разрешён любому авторизованному пользователю.

Деактивация клиента запрещает новые запросы и использование его JWT, отзывает
сессии через listener и отправляет `service.disabled`.
Повторная активация не восстанавливает отозванные сессии.
Команда `ops:broadcast` поддерживает `service-enable`, `service-disable`
и `test`; первые два режима действительно изменяют клиента в БД.

## Справочник API

Все пути ниже начинаются с `/api/auth` и требуют credentials клиента.
«JWT» означает дополнительную пользовательскую авторизацию.
Наличие маршрута не означает поддержку операции каждым провайдером.

| Метод | Путь | JWT | Назначение |
| --- | --- | --- | --- |
| POST | `/{provider}/otp` | Нет | Код для входа по телефону |
| POST | `/{provider}/login` | Нет | Вход |
| POST | `/{provider}/register` | Нет | Регистрация с паролем |
| POST | `/{provider}/register/verify` | Нет | Подтверждение регистрации |
| POST | `/{provider}/password/forgot` | Нет | Запрос восстановления |
| POST | `/{provider}/password/reset` | Нет | Сброс пароля и новый вход |
| POST | `/{provider}/password/change` | Да | Смена пароля |
| POST | `/{provider}/identifier/change` | Да | Начало смены телефона |
| POST | `/{provider}/identifier/change/confirm-old` | Да | Подтверждение старого номера |
| POST | `/{provider}/identifier/change/confirm-new` | Да | Подтверждение нового номера |
| POST | `/{provider}/account/delete` | Да | Запрос удаления |
| POST | `/{provider}/account/delete/confirm` | Да | Подтверждение удаления |
| POST | `/refresh` | Нет | Ротация пары |
| POST | `/logout` | Да | Завершение текущей сессии |
| GET | `/sessions` | Да | Активные сессии пользователя |
| DELETE | `/sessions/{session}` | Да | Отзыв выбранной сессии |
| GET | `/me` | Да | Декодированный JWT; в production возвращает 404 |

Точные маршруты — [routes/api.php](routes/api.php).
Примеры payload-ов и последовательностей запросов — коллекция
[Bruno](dev/IdentityService/).

В Bruno выберите окружение `Local`, заполните `clientId` и секретную переменную
`clientSecret`. Общие заголовки и инструкции сценариев находятся в `collection.bru`.
Токены сохраняются скриптами в runtime-переменные; после перезапуска нужен новый вход.
Для отзыва сессии задайте `sessionId` из списка, для broadcasting — `socketId`
реального WS-соединения. Коллекция предназначена для выбранных сценариев:
полный запуск подряд включает изменение паролей и удаление аккаунтов.

### Ошибки

Доменные auth-ошибки имеют вид `{"code": "INVALID_CREDENTIALS"}`.
Список значений — [AuthErrorCode](app/Exceptions/Auth/AuthErrorCode.php).
`OTP_THROTTLED` дополнительно возвращает `retry_after` в секундах.
Ошибки валидации используют стандартный Laravel JSON с `message` и `errors`, HTTP 422.

Для Шлюза важно различать `401 CLIENT_AUTHENTICATION_FAILED` и отказ в пользовательской
авторизации. Стандартная ошибка middleware `auth:id-api` может возвращать 401
без поля `code`; нельзя считать, что любой ответ 401 обязательно содержит доменный код.
Отсутствующий или некорректный refresh token возвращает `401 INVALID_REFRESH_TOKEN`,
а не обычную ошибку обязательного поля.

## Окружение и установка

Проект использует Laravel 13, Laravel Actions, JWT Auth и Spatie Permission.
В рабочем контейнере используется PHP 8.5; заявленное ограничение приложения
в Composer — `^8.3`. Устанавливайте зависимости по `composer.lock`,
с учётом требований всех пакетов и расширений.

Нужны Composer, подключение к БД и Redis с PHP-клиентом `phpredis`.
[.env.example](.env.example) выбирает SQLite; рабочее подключение определяется
конфигурацией окружения. OTP напрямую использует Redis. Cache и Laravel session
store в примере тоже настроены на Redis, но токеновые сессии находятся в БД.
Очередь по умолчанию синхронная (`QUEUE_CONNECTION=sync`), broadcasting — `log`.

В окружении владельца PHP, Composer и Linux-инструменты запускаются через
`IdentityServer` из корня проекта:

```sh
IdentityServer composer install
IdentityServer cp .env.example .env
IdentityServer php artisan key:generate
IdentityServer php artisan jwt:secret
```

Копирование `.env` предназначено только для первоначальной установки, когда файла
ещё нет. `jwt:secret` — вариант HS256. Для RS256 задаются `JWT_ALGO`,
`JWT_PUBLIC_KEY`, `JWT_PRIVATE_KEY` и при необходимости `JWT_PASSPHRASE`;
ключи можно подготовить через `jwt:generate-certs`.

После настройки БД **владелец самостоятельно** выполняет миграции и создаёт клиента
командой `client:create "Моё приложение"`. Если выбрана SQLite, сначала нужен её файл.
Секрет клиента печатается один раз; хранится только хеш.
У сервиса нет административного API управления клиентами.

### Сброс секрета клиента

Забытый секрет восстановить нельзя. Владелец может выпустить новый для существующего
клиента, сохранив его публичный `client_id`:

```sh
IdentityServer php artisan client:reset-secret <client_id>
```

Команда принимает значение `X-Client-Id`, а не числовой ID записи БД.
Она показывает новый `X-Client-Secret` один раз; в БД сохраняется только хеш.
Старый секрет сразу перестаёт проходить аутентификацию. Обновите его на Шлюзе
и в секретной переменной `clientSecret` окружения Bruno.
Сброс не активирует отключённого клиента.

Реализация — [ResetClientSecretAction](app/Actions/Auth/ResetClientSecretAction.php)
с отдельными `handle()` и `asCommand()`. В PHP тот же сценарий вызывается
через `ResetClientSecretAction::run($client)` и возвращает `ClientSecret`.
Таким образом, будущая панель сможет использовать его после своей проверки
административного доступа; панель и публичный endpoint сейчас не добавляются.

Команды миграций, seed, создания клиентов и изменения данных агентам запрещены
[правилами проекта](CLAUDE.md). `composer setup` включает `migrate --force`,
поэтому не является безопасной заменой ручной подготовки.

Для локального сервера доступен `IdentityServer php artisan serve`;
`IdentityServer composer dev` запускает настроенный Artisan dev workflow.

## Разработка и проверки

```sh
IdentityServer php artisan test --filter=SessionTrackingTest
IdentityServer composer test
IdentityServer composer analyze
IdentityServer composer pint
```

PHPUnit использует SQLite `:memory:`, array cache/session и sync queue.
`RefreshDatabase` и fixtures работают только в изолированной тестовой БД.
`ActsAsClient` готовит credentials клиента; OTP-тесты подменяют репозиторий
на `FakeOtpRepository`, чтобы не обращаться к рабочему Redis.
Один `CACHE_STORE=array` не изолирует прямые вызовы Redis.

Тесты охватывают клиентскую изоляцию, middleware priority, роли в JWT,
деактивацию, ротацию/отзыв сессий, восстановление пароля и broadcasting.
PHPStan/Larastan настроен на level 6, стиль проверяется Laravel Pint.

Правила для разработки — [CLAUDE.md](CLAUDE.md).
Локальные версии скиллов находятся в `.ai/skills/`; Boost синхронизирует их в
`.agents/skills/`. MCP подключается через отдельный `IdentityServerMcp`.

## Текущее состояние и ограничения

- SMS/email notifier-ы пока пишут коды в лог; настоящая доставка не подключена.
  При `APP_ENV=local` код всегда `1111`, в остальных окружениях генерируется случайно.
- Broadcasting по умолчанию пишет в лог. Рабочий WebSocket-транспорт не установлен
  настройками по умолчанию. До подключения реального транспорта нужно сузить
  разрешения канала `otp-deliveries`, сейчас доступного любому авторизованному пользователю.
- Нет публичного API привязки нескольких identities, восстановления удалённого
  аккаунта или администрирования клиентов. Ротация секрета доступна через Action
  и команду `client:reset-secret`, без публичного HTTP endpoint.
- `CurrentClient` — singleton с предположением об изоляции HTTP-запросов.
  Запуск в постоянных workers, например Octane, требует отдельной проверки жизненного
  цикла клиентского и пользовательского состояния.
- Настроенной CI-конфигурации в репозитории нет.
